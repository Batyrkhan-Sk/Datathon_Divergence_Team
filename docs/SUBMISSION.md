# Контроль кассовой дисциплины — решение команды Divergence (ForteBank Datathon 26)

AI-сервис анализирует видеозапись рабочего места кассира и сообщает о визуально
наблюдаемых признаках возможных нарушений кассовой дисциплины. По каждому эпизоду он
указывает тип, таймкод, кадры-доказательства, описание увиденного и правило со ссылкой на
нормативный акт РК. Результат является подсказкой для проверяющего, а не юридическим
заключением.

## 1. Адреса и доступ

| | |
|---|---|
| Веб-интерфейс | https://eggbeater-stardom-unsaid.ngrok-free.dev (при первом открытии в браузере ngrok показывает страницу-предупреждение — нажать «Visit Site») |
| API | `https://eggbeater-stardom-unsaid.ngrok-free.dev/api/v1/analyze` (POST), `https://eggbeater-stardom-unsaid.ngrok-free.dev/api/v1/jobs/{job_id}` (GET) |
| Ключ API | передаётся в форме сдачи; заголовок `X-API-Key` |

Запрос без верного ключа отклоняется (HTTP 401). Пример:

```bash
curl -X POST https://eggbeater-stardom-unsaid.ngrok-free.dev/api/v1/analyze -H "X-API-Key: <ключ>" -F "file=@video.mov"
curl https://eggbeater-stardom-unsaid.ngrok-free.dev/api/v1/jobs/<job_id> -H "X-API-Key: <ключ>"
```

Ответ соответствует схеме из ТЗ: `job_id`, `status` (`processing|done|failed`), `verdict`
(`violation|no_violation`), `violations[]` с полями `type`, `timecode_sec`, `description`,
`evidence_frames[{timestamp_sec, image_base64}]` (1–3 кадра JPEG). Дополнительно
(не мешает схеме): `type_id`, `confidence`, `rule {document, clause, quote, url}`.

## 2. Запуск и использование

**Пользователь:** открыть веб-интерфейс → загрузить `.mov` → дождаться обработки (обычно
5–20 с) → получить вердикт, карточки эпизодов с таймкодом, описанием, правилом, кадрами и
переходом к моменту на видео. Блок «Что проверил сервис» показывает по каждому типу нарушения:
найдено / не обнаружено / не проверено с причиной (например, «ноутбук не виден в кадре»), чтобы
проверяющий видел охват проверки и на чистом видео, и при другом ракурсе камеры. Отчёт по
видео можно скачать (HTML, открывается без интернета, печатается в PDF).

**Развёртывание** (Linux + NVIDIA GPU; проверено на RTX A6000, работает и на 4 GB GPU с
малой VLM):

```bash
python -m venv env && env/bin/pip install -r requirements.txt -r backend/requirements.txt
env/bin/pip install torch torchvision --index-url https://download.pytorch.org/whl/cu126
env/bin/pip install -r requirements-ml.txt
echo "API_KEY=<ключ>" > .env
bash deploy/run_server.sh        # сервис на :8000 (модели загружаются при старте)
bash deploy/run_tunnel.sh        # (опционально) публичный HTTPS-адрес
bash deploy/watchdog.sh          # (опционально) автоперезапуск сервиса и туннеля
```

**Локальность и переносимость:** все модели работают внутри сервиса; обращений к облачным
AI-сервисам нет. После однократной загрузки весов сервис работает без интернета
(`HF_HUB_OFFLINE=1`), поэтому его можно перенести во внутренний контур банка: достаточно
скопировать папку проекта вместе с весами моделей (`hf_cache/`, ~22 ГБ). **Проверено:**
при полностью заблокированном выходе в интернет модели загружаются из локальных файлов
(8 с), анализ видео выполняется полностью (X-26, X-20, X-29 — те же результаты).
Веб-интерфейс не использует внешних ресурсов (CDN, веб-шрифтов).

**Публичный адрес:** сервис работает на GPU-сервере команды. Внешний адрес обеспечивает
туннель ngrok (резервный — Cloudflare Tunnel). Туннель — это только сетевой транспорт:
он передаёт HTTPS-запросы на наш сервер и не выполняет никакой обработки. Весь анализ
видео (детекция, VLM, формирование результата) выполняется исключительно на нашем сервере.
При развёртывании во внутреннем контуре банка туннель не нужен.

**Обращение с загруженными видео:** загруженные файлы хранятся на сервере только для
обработки и удаляются автоматически не позднее чем через 24 часа. Они не используются для
обучения или настройки моделей, не публикуются и не передаются третьим лицам; в результат
(API и интерфейс) попадают только кадры-доказательства по этому же видео.

## 3. Архитектура и подход

```
.mov → декодирование (2 кадра/с) → восприятие → временная шкала состояний → детекторы
     → (проверка VLM на кропах) → кадры-доказательства + описание + правило → JSON
```

1. **Восприятие:** RT-DETR v2 находит людей, ноутбук, чашки. Люди за стеклянной стеной
   и отражения отсекаются по размеру и положению.
2. **Сцена определяется для каждого видео заново** (рабочее место, стол, сейф), без
   фиксированных координат. Это и даёт устойчивость к другому ракурсу камеры. Если
   ноутбук на новом ракурсе не виден, рабочее место определяется по месту, где кассир
   находится большую часть записи; проверка экрана в этом случае не выполняется.
3. **Детекторы — правила во времени** над состояниями: «кассир встал и вышел из
   помещения», «в помещении ≥ 3 человек ≥ 5 с», «в помещение, где кассир работает один,
   вошло второе лицо» и т. п. Таймкод — момент начала нарушения.
4. **Точечные вопросы к VLM на увеличенных кропах** (сейф, стол) вместо оценки всего видео:
   «дверца сейфа открыта?», «на столе лежат личные вещи?». Ответ берётся как вероятность
   «да», а решение принимается только при устойчивости в нескольких кадрах.
5. **Описание** составляется из шаблона по наблюдаемым фактам. **Ссылка на правило
   копируется дословно** из каталога `data/rules.json` и не генерируется моделью.

**Модели (только open source с коммерческой лицензией):**

| Модель | Задача | Лицензия |
|---|---|---|
| RT-DETR v2 R18 (`PekingU/rtdetr_v2_r18vd`) | люди, ноутбук, чашки | Apache-2.0 |
| OWLv2 (`google/owlv2-base-patch16-ensemble`) | деньги, монеты, сумка на кропе стола | Apache-2.0 |
| Qwen3-VL-8B-Instruct (на 4 GB GPU — Qwen3-VL-2B в 4-bit) | состояние сейфа, вещи на столе, поиск сейфа | Apache-2.0 |

Распознавание и идентификация лиц не используются; звук не используется.

## 4. Нормативные источники и сопоставление с видео

Использованы только акты РК (adilet.zan.kz):

| Ключ | Акт |
|---|---|
| НБРК № 231 | Постановление Правления НБРК от 29.11.2019 № 231 «Об утверждении Правил осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей…» — https://adilet.zan.kz/rus/docs/V1900019680 |
| НБРК № 14 | Постановление Правления НБРК от 24.02.2020 № 14 «Об утверждении Правил организации охраны и устройства помещений банков второго уровня…» — https://adilet.zan.kz/rus/docs/V2000020075 |
| АРРФР № 53 | Постановление Правления АРРФР от 03.04.2026 № 53 «Об утверждении Требований к обеспечению информационной безопасности банков…» — https://adilet.zan.kz/rus/docs/V2600038336 |

**Принцип сопоставления:** для каждого типа нарушения в `data/rules.json` записаны
(а) что должно быть **видно** на записи, (б) пункт акта и **дословная цитата**,
(в) степень применимости («прямо», «трактовка», «косвенно»). Все 18 цитат сверены с
текстами актов дословно. Описание фиксирует только видимое (например, «дверца сейфа
остаётся открытой 8 с»), а не невидимые факты (заперт ли замок, проведена ли операция).

## 5. Распознаваемые типы нарушений

| Тип | Что видно на записи | Норма |
|---|---|---|
| Наличные/ценности оставлены без присмотра | кассир встал и вышел; на столе остались деньги, монеты, сумка | НБРК № 231 п. 20 ч. 2; п. 22 |
| Рабочая станция не заблокирована | кассир вышел; на экране открыто рабочее приложение | АРРФР № 53 п. 71 подп. 9) (косвенно) |
| Посторонний в зоне кассовых операций | ≥ 3 человек; вход второго лица в помещение, где кассир работает один | НБРК № 14 п. 16 подп. 1), п. 8 |
| Сейф оставлен открытым | дверца сейфа открыта ≥ 6 с | НБРК № 231 п. 20 ч. 2, п. 80 (трактовка) |
| Личные вещи, еда, напитки | чашка/бутылка у кассира; одежда или сумка появились на столе | НБРК № 231 п. 12 |
| Инкассаторская сумка в зоне кассира: требуется проверка целостности и пломбы | на столе появилась сумка, по виду инкассаторская; сервис просит проверить по записи осмотр пломбы | НБРК № 231 п. 24 подп. 3)–4) |

## 6. Ограничения и известные ошибки

- **Ключ, оставленный в замке сейфа,** не распознаётся: на записи это несколько пикселей
  (обучающие X-22, X-13). Нужна камера с более высоким разрешением на сейф.
- **Дверь кассы оставлена открытой без входа посторонних** (X-32) и **пересчёт после
  ухода клиента** (X-34) не распознаются: один пример на тип, надёжного визуального
  признака нет.
- **Ручной пересчёт без счётной машины** (X-47, X-1, X-44) и **вход постороннего при лежащих на
  столе наличных** (X-4) не распознаются: деньги на столе во время обслуживания клиента —
  обычная ситуация, такое правило давало ложные срабатывания.
- **Таймкод** может отличаться от разметки на несколько секунд, если нарушение
  развивается постепенно (вход постороннего).
- Если ноутбук в кадре не виден, нарушение «экран не заблокирован» не проверяется, а
  остальные проверки работают по оценённому рабочему месту (проверено на обучающих
  видео с искусственно скрытым ноутбуком: 10 из 22, без ложных срабатываний).
- Порог «экран не заблокирован» откалиброван под вид рабочего приложения в обучающих
  видео; на другой технике возможны пропуски.
- Правила подобраны на 40 уникальных обучающих видео (5 вариантов размещения); на новом
  ракурсе качество может быть ниже. Проверено поблочно по вариантам размещения.

## 7. Результаты на обучающей выборке

Прогон `eval/run_eval.py` на 42 размеченных видео (40 уникальных: X-47 = X-4,
X-48 = X-5), сервер с RTX A6000:

| Метрика | Значение |
|---|---|
| Найдено нарушений (по видео) | **13 из 22** (уникальных: 13 из 21) |
| Ложные срабатывания на чистых видео | **0 из 20** |
| Точность вердикта (уникальные видео) | **80 %** (precision 100 %, recall 62 %) |
| Таймкод в пределах 2 с от разметки | 85 % |
| Верный тип (± 3 с от разметки) | 92 % |
| Время обработки видео | 6,7 с в среднем, 21 с максимум (лимит — 5 мин); 3 видео одновременно — до 22 с |

По вариантам размещения (A–E — пять разных комнат и ракурсов) ложных срабатываний нет ни
в одном; полнота от 50 % до 75 %. Для сравнения: оценка «всего видео целиком» большими
VLM (27–38B) в похожем эксперименте давала точность 40–60 %.

**Проверка устойчивости к другому ракурсу.** Чтобы не переобучиться на обучающих видео,
мы прогнали сервис на тех же 42 видео, искусственно изменённых так, будто их снимала
другая камера (разметка сохраняется):

| Вариант | Найдено нарушений | Ложные срабатывания |
|---|---|---|
| Исходные видео | 13 из 22 | 0 из 20 |
| Зеркальное отражение (комната «наоборот») | 12 из 22 | 0 из 20 |
| Наклон / смещение камеры (перспектива) | 12 из 22 | 0 из 20 |
| Камера ближе (приближение 15 %) | 10 из 22 | 0 из 20 |
| Камера хуже (половинное разрешение, размытие, темнее) | 7 из 22 | 0 из 20 |
| Ноутбук не виден (рабочее место по положению кассира) | 10 из 22 | 0 из 20 |

Первый прогон выявил хрупкие правила (по одному ложному срабатыванию на отражении,
наклоне и приближении). Мы исправили их общими правилами, а не подгонкой под видео:
уход кассира засчитывается, только если помещение остаётся пустым до конца записи или
≥ 6 с; группа из 3 человек — ≥ 7 с или до конца записи; движение чашки измеряется
относительно её размера; найденная детектором чашка подтверждается VLM на широком кропе (чашка — да, банкноты — нет: свёрнутая пачка денег в руке похожа на чашку). После
исправлений результат на исходных видео не изменился, а **ложных срабатываний нет ни в
одном варианте**.

**Честная оговорка:** правила подбирались на этих же видео, поэтому оценка на них
оптимистична. На новом ракурсе ожидаем снижение полноты (как в таблице выше) при
сохранении низкого уровня ложных срабатываний. При заметно худшем качестве видео полнота
падает сильнее: проверка наличных и экрана требует достаточной чёткости.
